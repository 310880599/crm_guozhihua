## 1. 业务目标与范围

### 1.1 业务目标

代替原有业务员以文字向产品经理提出发货请求的流程，实现：

```text
销售选择已审核通过的成交订单（1张）
  ↓
选择订单产品 → 编辑本次发货行（产品名、型号、数量、采购单价、销售单价、厂家）
  ↓
保存草稿，或正式提交审核
  ↓
相关产品经理审核（多人时各审自己负责的行；全部通过才能流转）
  ├─ 驳回 → 整单退回销售 → 修改 → 新轮次重新审批
  └─ 全部通过
        ↓
      按【原订单总金额】与审批阈值比较
        ├─ 低于阈值 → 审批通过，并按规则抄送
        └─ 达到/超过阈值 → 产品总监审核 → 审批通过并抄送
        ↓
按厂家分组生成独立厂家发货清单
  ↓
各厂家登录各自账号 → 查看本厂清单 → 接单并承诺发货时间范围
  ├─ 无法接单 → 内部退回、修改厂家、重新审批（原清单失效）
  └─ 已接单 / 待发货
        ↓
厂家按次填报实际发货数量、物流/车辆司机、附件
  ↓
部分发货 / 已全部发货 → 内部通知与进度汇总
  ↓
以实际发货记录为依据进行月/年统计与厂家对账
```

### 1.2 明确不做或后置

- 不允许一次申请关联多张成交订单。
- 不采用“一个发货行同时绑定两个厂家”；有此情况必须新增第二条发货行。
- 现阶段**不开发销售端/客户收货确认**；以后有需要再立项。
- 补发属于后期独立功能；与正常分批发货严格区分。
- 暂不开发短信、微信消息、独立复杂工作流引擎。
- 不要求一次完成所有功能；按里程碑交付。

## 2. 不得擅自改变的已确认业务规则

### 2.1 订单、产品行与厂家

**BR-01【已确认】** 一张发货申请只能关联**一张**已审核通过的原成交订单（`crm_client_order.check_status=2`）。

**BR-02【已确认】** 一张订单可以多次申请发货；允许部分发货。

**BR-03【已确认】** 每张申请可包含原订单的一行或多行产品；每条**发货行只指定一个固定厂家**。

**BR-04【已确认】** 不同行可指定不同厂家；同一原订单产品也可复制/新增发货行，分别指定厂家；新增行应继续关联同一个有效原 `order_item_id`，而不是伪造原订单新产品。

**BR-05【已确认】** 同一 `order_item_id` 在一张申请中允许出现多条发货行；服务端必须**按原订单产品 ID 汇总**本次所有行的数量，与其他有效申请已占用数量合并校验，不可超出剩余可发量。

**BR-06【已确认】** 同一厂家收到同张申请中的多行产品时，审批通过后形成**同一张厂家清单**；不同厂家各自生成清单，独立接单、承诺交期、发货和记录状态。

**例：** 原订单：划线机 2 台、热熔釜 2 台、涂料 1 吨；本次三行分别指定厂家 A/B/C → 审批通过后生成 3 张独立厂家清单。

**例：** 原订单划线机 10 台，本次第 1 行 4 台给厂家 A、第 2 行 2 台给厂家 B → 按同一原产品合计 **6 台**。若剩余仅 5 台必须拒绝提交。

### 2.2 编辑和价格

**BR-07【已确认】** 本次发货允许修改**产品名称、型号、发货数量、采购单价、销售单价、厂家及必要备注**；产品经理重新确认修改后的信息，错误可驳回，业务员修改后重新提交。

**BR-08【已确认】** 发货申请修改不反写原 `crm_client_order` / `crm_order_item` 的产品、成交价、订单金额和利润。原订单快照与本次发货字段分开存储。

**BR-09【已确认】** 本次采购价格按**采购单价**填写，本次采购金额 = 本次发货数量 × 本次采购单价；计算使用金额定点精度，禁止用浮点误差作为财务结论。

**BR-10【已验证】** 原 `crm_order_item.purchase_price` 的实际语义为**整行采购金额合计**，不是采购单价；不得直接沿用其字段名承载 V2 采购单价。

### 2.3 草稿、正式提交与审批

**BR-11【已确认】** 草稿不占用剩余发货数量；**正式提交审核**才占用。草稿保存可放宽部分必填项，但提交必须完整校验厂家、产品、数量、收货信息等。

**BR-12【已确认】** 当前数量占用的发货申请状态是 `10` 待产品经理、`30` 待总监、`50` 审批通过；`0` 草稿、`20/40` 驳回、`60` 取消不占用。若要变更，须另行评审并同步修改历史数据策略。

**BR-13【已确认】** 正式提交时读取审批配置并保存快照；判断依据为**原订单总金额**，**不是本次申请产品金额**。金额 `< approval_threshold`：经理通过后完成；金额 `>= approval_threshold`：全部经理通过后再由产品总监审批。当前阈值默认配置为 10000 元，**等于 10000 元也必须走总监**。

**BR-14【已确认】** 低于阈值经理审批完成后抄送产品总监、超级管理员、销售主管、财务；达到阈值则总监审批完成后抄送超级管理员、销售主管、财务。实际配置从 `crm_shipping_config` 读取。

**BR-15【设计约束】** 一张申请涉及多个产品经理时，推荐一人一任务，各自只审自己产品行；任一驳回整单退回，旧轮次任务全部失效；重新提交开启新 `approval_round`，历史日志保留。

### 2.4 厂家权限与履约

**BR-16【已确认】** 厂家端**仅可查看与本厂家结算相关的采购价格**；不显示销售价、利润、提成及其他厂家清单。其他客户敏感字段按业务最小必要开放，不能默认全量返回。

**BR-17【已确认】** 厂家无法接单，退回内部修改厂家后**重新审批**。原厂家清单必须失效/撤销访问权限，不能使新旧厂家同时接单。

**BR-18【已确认】** 暂不做客户收货确认；后续预留厂家补发能力，用于运输损坏、少发漏发、错发等异常。正常剩余数量后续发出属于**分批发货**，不属于补发。

**BR-19【建议待实施时确认】** 一张厂家清单可多次实际发货；按行控制累计实发数量，部分发货与全部发货分别标识。

### 2.5 财务与统计

**BR-20【已确认的方向】** 经理要求财务按月、按年汇总并导出；统计基础是**真实的已确认发货记录**，不能以“申请数量/审批通过数量”冒充实发。

**BR-21【待确认】** 具体月度归属时间、运费承担、补发是否形成厂家应付款、退货/折让、付款对账细则未最终定稿，不能在代码中擅自固化。

## 4. 总体技术设计原则

1. **增量升级**：保留已有六张表，优先扩展 `crm_shipping_apply_item`；避免重写已有正常功能。
2. **一申请一原订单**：主表继续保存一个 `order_id`；同一原订单可产生多张申请。
3. **快照分层**：原订单产品与价格快照、本次发货业务信息、厂家履约实际记录三层分离。
4. **一行一厂家**：每条发货行唯一厂家 ID；厂家清单按厂家 ID 分组生成；同厂多行合并一张清单。
5. **状态机分离**：申请审批状态、厂家清单履约状态、实际发货记录状态分开维护，不混在同一个 `status` 中。
6. **服务端是真实边界**：权限、数值、金额、归属、状态流转、并发校验均不能只依赖前端。
7. **事务与幂等**：保存/提交/审批/生成厂家清单/接单/确认实发必须考虑重复点击和并发。
8. **审计可追溯**：审批轮次、驳回理由、厂家拒单、物流回填、补发、关键修改应保留可核查历史。
9. **最小权限**：厂家角色只允许本厂清单，不依赖菜单隐藏进行隔离。
10. **先设计再执行 SQL**：每次结构改动都先评审字段类型、默认值、索引、影响范围、备份与回退。

## 5. 数据库关系目标（逻辑模型，非建表命令）

```text
crm_client_order（一张原订单）
    ├── crm_order_item（原订单产品明细）
    └── crm_shipping_apply（多次发货申请，每次只关联1个订单）
          ├── crm_shipping_apply_item（本次发货行：可多行指向同一order_item）
          ├── crm_shipping_approval_task（按审批人/轮次）
          ├── crm_shipping_approval_log（审批操作历史）
          ├── crm_shipping_cc（抄送/已读）
          └── crm_shipping_factory_bill（审批完成后按厂家分组生成）
                ├── crm_shipping_factory_bill_item（关联发货行）
                └── crm_shipping_delivery（多次实际发货）
                      ├── crm_shipping_delivery_item（每次实发对应产品行）
                      └── crm_shipping_attachment（物流凭证）

crm_product_category（待核验可否作为现有厂家主档）
    └── crm_supplier_admin（厂家与CRM账号绑定，后续阶段）
```

**设计待评审事项：** `approval_round` 在哪些表新增；原采购金额快照与采购单价字段；发货行行号；旧草稿版本识别；厂家清单/实发关联唯一键；财务对账来源明细的防重复索引。

3. 原订单快照与本次发货字段的映射表；`purchase_price` 仍按原订单**整行进价**理解。
4. 对旧草稿的兼容策略（包括缺厂家/价格，失效 `order_item_id`，订单金额变化）。
5. 并发数量锁定策略；同一原产品多行的汇总 SQL/伪代码；草稿不占用。
6. 申请主表、审批任务/日志 `approval_round` 的后续结构预留。
7. 厂家主档 `crm_product_category` 的语义复核，以及厂家账号权限结构建议。
8. **待审核的** `ALTER TABLE` SQL 草案、执行前检查 SQL、影响及可能锁表风险、备份/回退方案；**绝不执行**。

**验收清单**：

- [ ] 每个新增字段具备清晰的“原快照 / 本次值”语义。
- [ ] 采购单价、数量、采购金额、销售单价的精度与舍入规则一致。
- [ ] 当前六表全部保留，未无必要地增加厂家主档。
- [ ] 旧 V1 草稿可打开；遇失效行明确提示重选，不能静默指向其他产品。
- [ ] 同一 `order_item_id` 分拆多行可建模；不破坏原订单数据。
- [ ] 只读分析阶段没有执行 ALTER、UPDATE、DELETE、INSERT 或修改项目文件。
- [ ] SQL 和回退计划已经人工审查通过。

**阻塞条件**：旧草稿恢复策略不明；供应商 ID 无法稳定定位；数量并发锁范围不清；价格定义仍存在二义性。

### M3｜发货申请 V2 与草稿（数据库执行须单独授权）

**界面目标**：一张已审核订单 → 可增删多条发货行 → 每行产品名称/型号/数量/采购单价/销售单价/厂家可编辑 → 保存草稿 / 重新打开。

**开发任务**：

- [ ] 执行经审核的最小数据库 ALTER（先备份、记录执行结果）。
- [ ] 修改订单明细转发货行逻辑；前端新增、复制、删除行。
- [ ] 发货行使用独立 ID（新增行临时键/保存后行 ID），不再用 `order_item_id` 作为前端唯一行标识。
- [ ] 同一原订单产品多行时，编辑回填不丢行、不串厂家。
- [ ] 原订单快照由服务端生成；本次可编辑值独立保存；只更新发货相关表。
- [ ] 整数数量严格校验，不允许小数、混合字符串、负数及非法数组。
- [ ] 按 `order_item_id` 汇总当前行数量并结合已占用数量检查；事务锁与并发策略验证。
- [ ] 草稿数量不占用；零数量行按已确定规则跳过；至少保留一行正数申请量。
- [ ] 保存草稿可允许厂家等后续提交必填字段暂缺；恢复编辑后不丢数据。
- [ ] 失效原订单产品行或已改变订单的草稿给出明确阻断/重选提示。
- [ ] 修复或验证输入输出转义，防止产品名、备注等 HTML 属性/XSS 注入。
- [ ] 明确权限：仅订单对应销售、特定经办人以及超级管理员按已定权限可建申请；不能因 V2 扩权。

**关键用例（至少人工 + 接口测试）**：

| TC | 用例 | 预期结果 | 实测 |
|---|---|---|---|
| M3-01 | 一个订单三行，分别厂家 A/B/C | 保存后每行厂家正确，重新打开不丢行 | 待测 |
| M3-02 | 同一个 `order_item_id` 拆 4+2，两厂 | 两行都保留，总量正确 | 待测 |
| M3-03 | 剩余 5，拆成 4+2 | 服务端拒绝，事务回滚 | 待测 |
| M3-04 | 已有有效申请占 4，剩余 6，本次再申 7 | 拒绝超量 | 待测 |
| M3-05 | 两张草稿引用同一原产品 | 均可保存草稿，不占用；提交阶段再竞争 | 待测 |
| M3-06 | 修改产品名、型号、两种单价 | 仅发货表改变，原订单不变 | 待测 |
| M3-07 | 编辑草稿复制行、更换厂家、删除行 | 保存与回填一致，无残留行 | 待测 |
| M3-08 | 伪造他人 `order_id` / `order_item_id` | 后端拒绝 | 待测 |

### M4｜正式提交、产品经理/总监审批、抄送及厂家清单

**任务**：新增“提交审核”，让审批按配置和真实订单快照流转；审批完成后**幂等**生成厂家清单。

- [ ] 正式提交重新读取订单状态、订单金额、有效产品行、数量、厂家和地址；事务内加锁校验。
- [ ] 提交时写入审批阈值、路线、产品总监、财务、主管等快照。
- [ ] `<10000`（以当前配置阈值代指）：仅产品经理；`>=10000`：经理通过后进入总监（实际测试从数据库读阈值）。
- [ ] 多位产品经理各一任务；仅能查看/审核自己负责的产品行。
- [ ] 驳回整单退回；旧轮全部任务失效，重提新一轮，日志保留。
- [ ] 审批并发与重复点击幂等，不会多次产生有效任务或清单。
- [ ] 抄送收件人、抄送触发时间与已读状态正确；避免轮次唯一键冲突。
- [ ] 正式审批通过后申请内容只读；受控变更/撤销机制单独设计。
- [ ] 按 `factory_id` 分组，每个厂家一张独立清单；清单明细与申请行稳定关联。
- [ ] 不给草稿、驳回申请或未最终通过申请生成厂家清单。

| M4-02 | 原订单 10000 | 必须进总监审批；等于阈值不漏审 |

### M5｜厂家账号、权限与接单

- [ ] 核实并复用现有厂家主档；新增必要的厂家账号绑定和角色权限。
- [ ] 一厂家可多个账号；一期一个账号只绑定一个厂家（建议，实施前核实）。
- [ ] 厂家登录仅看到属于自己的清单；所有读写接口服务端强校验归属。
- [ ] 厂家可看本厂采购价格，不返回销售价、利润、提成及其他厂家的清单。
- [ ] 接单时填写承诺发货时间**范围**；校验起止时间。
- [ ] 无法接单填写原因，触发内部处理；修改厂家需重新审批，旧清单失效且不可再操作。
- [ ] 同一清单重复点击接单、伪造 ID、账号停用及账号切换均不越权。

**验收**：厂家 A 不能读取或修改厂家 B 的任何清单；对所有 API 做越权测试，不仅检查 UI 菜单；拒单后不能出现两张同时有效的厂家任务。

### M6｜实际发货、物流、附件与通知

- [ ] 一张厂家清单可记录多次正常实际发货，每次对应产品行数量。
- [ ] 普通快递/物流、专车、客户自提、其他方式字段按需填写。
- [ ] 保存物流公司/运单号或司机/电话/车牌、实际发货时间、备注。
- [ ] 文件采取白名单、MIME/后缀检查、大小限制、私有存储、下载权限校验；不开放任意可执行类型。
- [ ] 首次实发不足 → 部分发货；累计全部完成 → 已全部发货。
- [ ] 同清单多次并发确认仍不超发；提交接口幂等。
- [ ] 业务员、相关经理、总监、财务、管理员按权限看到进度与物流。
- [ ] 关键事件站内提醒/角标；不因通知失败丢失主发货记录。

**验收**：应发 10，先发 6、后发 4 → 累计 10；再发 1 → 拒绝；厂家 B 无法查看厂家 A 附件；重复确认不能产生两次实发。

### M7｜补发、财务对账与月年报表（后续阶段）

- [ ] 正常分批与异常补发分开建模；补发必须关联原清单/原实发及原因。
- [ ] 补发经内部产品经理确认，不允许厂家自行提高原订单发货目标量。
- [ ] 明确补发是否计入厂家应付款、谁承担运费等业务规则后再开发。
- [ ] 月/年统计使用已确认实发记录；定义统一统计时间与对账归属期。
- [ ] 厂家对账单按发货来源明细防重复计算，支持调整、确认、导出。
- [ ] 财务付款状态与“已发货”状态区分；管理层报表有权限约束。

**验收**：同一实发来源不能被重复入账；补发与正常发货单独可追踪；月年汇总可追溯到来源明细，抽样手工核算一致。

### M8｜全流程联调、上线与稳定运行

- [ ] 业务员、产品经理、总监、销售主管、财务、超级管理员、厂家账号分别完成权限回归。
- [ ] 全流程：草稿 → 提交 → 审批 → 清单 → 接单 → 分批实发 → 通知 → 对账。

## 8. 安全、数据一致性与回归底线

### 8.1 必须作为阻断项的风险

- **P0：** 厂家能看到别家清单/内部销售利润；普通用户越权提交或审批；正式提交后超发；重复生成有效厂家清单；原订单被发货申请覆盖；恶意附件可执行或越权下载；驳回后旧审批继续生效。
- **P1：** 旧草稿丢行、金额/厂家快照串行；并发重复记录；供应商 ID 混淆；不同发货行被错误合并；错误日期造成统计错期；审批配置快照缺失。
- **P2：** 页面提示、布局、筛选、非关键性能与用户体验细节。

### 8.2 核心技术控制点

- 输入严格验证：数量整数；价格 `DECIMAL` 精度与非负规则；ID 正整数；日期范围；字符串长度与输出转义。
- 关联验证：`order_item_id` 必须属于本申请的 `order_id`；`factory_id` 必须是有效厂家；经理 ID 必须来源可信服务端数据。
- 锁与占用：草稿不占；提交前事务内检查 `[10,30,50]` 占用；多行同产品汇总；不同请求的锁顺序一致。
- 审批结果与清单不可变：审批完成后产品/厂家/金额快照固定，后续变更应通过受控失效和重新审批流程处理。
- 文件：复用合同附件的私有文件、MIME 白名单、鉴权下载模式；存储路径不能被直接拼接访问。
- 日志：操作人、时间、动作、前后状态、审批轮次、原因等应可审计，避免直接物理删除关键证据。

## 9. 尚未最终确认的业务问题登记

这些问题**不得在 Cursor 编码时自行决定为“已确认”**：

| 编号 | 问题 | 当前建议/处理 | 最晚确认点 |
|---|---|---|---|
| D-01 | 本次发货销售价变化是否需要额外审批门槛？ | 默认仍由产品经理及原订单金额规则审批；额外门槛待经理确定 | M4 前 |
| D-02 | 厂家是否能看到客户全称、电话、具体地址？ | 最小必要：发货地址/联系人电话应可用；其余字段脱敏 | M5 前 |
| D-03 | 厂家基础资料 `crm_product_category` 是否混合普通分类？ | 专项只读核验，不直接假设全部都是厂家 | M2 |
| D-04 | 已审批通过但尚未接单的申请能否取消？ | 设计受控撤销，清单需联动失效 | M4 前 |
| D-05 | 厂家拒单后是否保留原清单与物流记录历史？ | 建议保留只读历史，取消可操作状态，重新审批后生成新清单版本 | M5 前 |
| D-06 | 一个厂家允许多个账号，一个账号是否绑定多个厂家？ | 建议一账号仅一厂家，一厂家多账号 | M5 前 |
| D-07 | 财务报表以实际发货确认时间还是业务交运时间为准？ | 推荐“已确认实发时间”，对账期间可单独定义 | M7 前 |
| D-08 | 补发是否计成本与应付款、运费谁承担？ | 财务规则需经理和财务确认，先不自动结算 | M7 前 |
| D-09 | 少发/错发/损坏需要怎样内部确认？ | 推荐产品经理审核补发原因及数量 | M7 前 |
| D-10 | 不同产品单位（台、吨）是否允许小数发货？ | **当前 V1 严格整数**；涂料“1 吨”可能需要小数，必须先确定单位级数量精度和数据库类型，禁止默认按整数推广至全部产品 | **M2 前，阻断** |

## 10. 每轮 Cursor 任务的标准操作流程

**第 1 步：只读分析**

- 明确本轮只分析的文件/方法/表、已确认规则与范围。
- 输出“现状 → 问题 → 最小方案 → 修改清单 → 风险 → 测试点”。
- 不改代码、不建表、不执行 DML/DDL、不提交 Git。

**第 2 步：方案评审**

- 核对是否与本文件 BR 编号冲突；特别检查数量、价格、权限、历史草稿。
- 对 SQL 草案审字段语义、索引、迁移顺序、备份/回退，不仅看语法是否正确。

**第 3 步：有限范围实施**

- 仅允许明确的文件和 SQL；不顺手重构无关模块。
- Cursor 报告变更文件、函数、关键差异、SQL（执行或未执行分开写）。
- 除非用户明确授权，不做 `git add / commit / push`、生产部署、数据库写操作。

**第 4 步：本地/测试环境验证**

- PHP lint、SQL 只读核对、接口正反测试、浏览器操作、权限测试、并发/重复提交用例。
